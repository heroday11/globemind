# GlobeMind Web Python Runtime

The versioned Web/API/CC Python role is selected from the repository `VERSION`
file by default. Derive the candidate target in the shell; do not copy a
version literal from a handoff into a build command:

```bash
runtime_version="$(tr -d '\r\n' < VERSION)"
runtime_dir="/root/data/python-runtimes/globemind-web/${runtime_version}"
```

A deliberate historical diagnostic must instead read the runtime version from
that selected release's immutable `release.json`.

Building a runtime does not select it for production. Current production and
the V1 rollback baseline remain build `0.11.0-20260710T223243Z` with versioned
runtime `/root/data/python-runtimes/globemind-web/0.11.0` while the source is
being closed for V1. The live
`/opt/conda/envs/Globemind_env` and long-pipeline `.env_torch` environments are
read only during a build.

## Dependency boundary

The authoritative direct input is `requirements/roles/web.in`; the complete
installation is `requirements/roles/web.lock`. The lock is generated by an
isolated `pip-tools==7.5.2` environment and contains exact versions and hashes
for CPython 3.11.15 on Linux x86_64.

The role contains:

- FastAPI, Uvicorn, HTTP clients, PostgreSQL, authentication and encryption.
- CC and assistant SDKs.
- NumPy, PyMilvus, CPU Torch, sentence-transformers and Transformers 5.1 for
  the current BGE compatibility fallback.
- Pillow, PyMuPDF, python-pptx, CairoSVG, reportlab, svglib, Requests and
  Beautiful Soup for document, image, PDF, SVG and PPTX entry points.
- Pytest tooling used by the candidate's own Web/API validation gate.

GLiNER and vLLM are excluded. vLLM remains an HTTP service. GLiNER belongs to
the pipeline role. Transformers is pinned below 5.2 to avoid carrying the
known shared-environment conflict forward.

The preferred BGE route is `BGE_M3_BASE_URL`, but no managed service currently
replaces the local compatibility path. Local fallback therefore remains
enabled, and the CPU model packages remain part of this role. The runtime does
not claim that a dedicated BGE service migration has happened.

Pandoc is a system executable, not a Python package. `doc_to_md.py` continues
to require a separately managed Pandoc installation. Its absence does not get
hidden by the Python lock.

## Regenerate the lock

```bash
deploy/build_python_runtime.sh lock
```

The command creates or reuses only
`/root/data/python-runtimes/.build-tools/pip-tools-7.5.2`. Proxy variables are
removed for package operations because this container advertises a SOCKS
proxy without the corresponding bootstrap dependency. PyPI and the exact
official CPython 3.11/Linux x86_64 PyTorch CPU wheel remain explicit in the
lock metadata. The wheel uses a direct URL so unrelated packages are never
resolved through a secondary index. User-level pip configuration is disabled;
the host's configured mirror does not participate in resolution or install.

## Build and verify

```bash
deploy/build_python_runtime.sh build
deploy/build_python_runtime.sh verify
```

Both commands target the version in `VERSION`. For read-only investigation of
an existing immutable release, derive any explicit override from its manifest:

```bash
selected_release="$(readlink -f /root/data/releases/globemind/current)"
selected_runtime_version="$(
  /usr/bin/python3 -B - "$selected_release/release.json" <<'PY'
import json
import sys

print(json.load(open(sys.argv[1], encoding="utf-8"))["python_runtime"]["version"])
PY
)"
RUNTIME_VERSION="$selected_runtime_version" deploy/build_python_runtime.sh fingerprint
```

The builder:

1. Acquires a role lock and fingerprints the input, hash lock, builder,
   CPython binary and platform.
2. Records package-list hashes for both live environments.
3. Creates a temporary copied venv and installs only the hash-locked entries.
4. Runs `pip check`, critical and application import closure, and selected
   non-live/non-GPU Web/API/CC tests. The gate includes database and identity
   boundaries, search and retired endpoints, feature contracts, runtime catalog
   closure, and database-consumer inventory contracts.
5. Confirms both live environment package hashes are unchanged.
6. Rewrites temporary console-script and `pyvenv.cfg` prefixes, removes
   group/world write permissions, verifies the inventory, and promotes with an
   atomic no-clobber directory rename.

An existing target with the same build-input fingerprint is verified and
reused. The same version with a different fingerprint is rejected; it is never
overwritten. This preserves every older runtime as historical evidence even
after the builder evolves: a new builder cannot silently rebuild that version.
Symlinks and non-directory targets are rejected. Promotion records the
candidate device and inode; failure cleanup removes a promoted target only
while that identity is unchanged. Internal runtime links must be relative,
non-dangling, and resolve inside the runtime root. No production process,
release, database, model service or long-running pipeline is changed.

The venv owns its site-packages but records the read-only CPython base at
`/opt/conda/envs/Globemind_env`. Replacing that CPython distribution requires
a new runtime version and rebuild; copying this directory to a different host
is not claimed to be portable.

## Inventory

Each promoted runtime contains:

- `inventory/runtime.json`: build and runtime fingerprints, Python provenance,
  lock hash and gate results.
- `inventory/pip-freeze.txt`: sorted installed distribution inventory.
- `inventory/import-closure.json`: critical imports and loaded distributions.
- `inventory/pip-check.txt` and `inventory/pytest-web.log`: validation evidence.

Existing inventories and installations remain immutable and are still checked
by the focused runtime-builder tests when explicitly selected. Repository and
CI test runs do not inspect a host runtime by default; this keeps the suite
portable and prevents a checkout from depending on machine-local evidence. To
include an isolated promoted runtime in a deliberate validation run, set
`GLOBEMIND_TEST_PROMOTED_RUNTIME` to its absolute runtime directory before
running `backend/tests/test_python_runtime_build.py`. Never point this variable
at a production release directory.

Selecting the runtime derived from `VERSION` requires a matching schema-v3
release, clean scoped provenance, candidate gates, two-phase promotion, and
rollback evidence; the builder alone never changes the launcher.
