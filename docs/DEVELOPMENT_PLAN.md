# 开发整理路线

本文记录源码仓库的工程治理方向，不代表生产发布承诺。每一阶段都应以小型、可回滚的 Pull Request 完成，并同步更新模块 README、契约测试与风险说明。

## 当前基线

- 根目录已提供统一开发入口、贡献规范、安全政策和 PR 检查模板。
- API、离线算法、脚本、前端、数据和部署目录已有各自的职责与安全边界说明。
- npm 已统一为锁文件驱动的安装方式；Vue 主站与金融终端保持独立测试和构建。
- 离线质量门禁覆盖测试、前端契约、受控 Ruff 目标、密钥扫描、配置/数据清单和源码稳定性。
- 历史代码仍有较多全仓 Ruff 债务、绝对路径和跨模块耦合；现有门禁是渐进基线，不应被描述为全仓静态检查已经清零。

## P0：稳定协作入口

- 在 GitHub 为 `main` 启用分支保护，要求质量门禁通过后合并；这是仓库管理员操作，不由源码提交自动开启。
- 确定项目许可证后再添加 `LICENSE`；在所有者选择前不猜测授权条款。
- 为安全报告配置真实的私密联系渠道或 GitHub Private Vulnerability Reporting。
- 保持凭据扫描与历史泄露处置流程；任何曾暴露的凭据都按已失效处理并轮换。

完成标准：新贡献者能从根 README 安装、测试并提交 PR，且公开页面不要求其接触生产凭据或运行环境。

## P1：收紧模块边界

- 将 `backend/api` 保持为 HTTP/应用层，逐步把离线任务从请求路径移出；通过接口而不是 `sys.path` 修改连接模块。
- 明确 `backend/agentic_rag` 与 `core_pipeline` 的公共 Python API，解决同名模块/包和从仓库根无法可靠执行的入口。
- 将 `frontend/knowledge_graph_backup` 迁入明确的 archive/compatibility 区，或在有负责人和可运行契约后恢复为独立应用。
- 为 Vue 主站和金融终端分别维护构建、类型检查和契约测试；共享代码只进入 `frontend/shared` 的稳定接口。

完成标准：每个模块可在自己的 README 所述边界内安装和验证，不依赖未声明的工作目录、绝对路径或其他模块内部实现。

## P1：分离源码、数据与产物

- 对 `data/` 做逐目录清单，只保留小型、脱敏、许可明确的 fixture/reference；运行状态、数据库、日志、模型权重和大规模语料移到仓库外受控存储。
- 为必须版本化的大文件选择 Git LFS 或带校验和的外部制品，不继续扩大普通 Git 历史。
- 持续检查 Docker build context，确保源码包被包含，`.env`、数据库、日志、checkpoint 和模型权重被排除。

完成标准：全新 clone 不携带运行状态或秘密，且开发者能明确知道如何取得可授权的测试数据和外部制品。

## P2：偿还历史质量债务

- 按目录逐步扩大 `run_quality_gate.sh` 的 Ruff 目标；每次先修复一个边界清晰的模块，再把它加入永久门禁。
- 清除硬编码的主机路径，将运行时位置放入受控配置，并为默认值和错误状态补契约测试。
- 给活跃文档增加 owner/status/last-verified 元数据；把阶段报告和实验记录迁入清晰的 archive 索引。
- 为 API 公共契约、数据库迁移和前端共享类型建立版本化变更说明。

完成标准：全仓静态检查能够启用，当前文档与历史证据容易区分，模块变更不会依靠隐式环境知识。
