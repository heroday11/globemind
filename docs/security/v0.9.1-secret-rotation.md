# V0.9.1 Secret Rotation Runbook

Do not rotate credentials or restart production as part of the source change. Use a maintenance window and keep the previous application encryption key until verification is complete.

## Exposure inventory

Rotate these credentials because their previous values were stored in tracked source, local environment files, process arguments, API responses, or browser storage:

1. PostgreSQL administrative/read/write credentials (`DB_*`, `PG_*`, `PG_WRITE_*`, `L1_DB_*`).
2. User-supplied provider keys stored in `public.app_user.api_keys`; notify affected users to rotate them at each provider.
3. Platform LLM/image credentials (`DEEPSEEK_*`, `PUBLIC_DEEPSEEK_*`, `HERMES_*`, `CLOUD_API_KEY`).
4. `JWT_SECRET_KEY`, `ADMIN_PASSWORD`, and any development/unified login password. `JWT_SECRET_KEY` rotation invalidates existing sessions and also changes the HMAC key used to verify the local identity-assurance event chain. Existing MFA/session audit ledgers must therefore be migrated or deliberately retired under an approved procedure before rotation; the application does not currently support a previous JWT integrity key.
5. SMTP credentials and tunnel/service tokens if they have shared the same readable environment or shell history.

Never include old or new values in tickets, command arguments, logs, or this repository.

## Initial encryption rollout

1. Back up `public.app_user(id, api_keys)` with restricted permissions and test restoration.
2. Generate a dedicated key with the locked Web runtime: `PYTHONDONTWRITEBYTECODE=1 /root/data/python-runtimes/globemind-web/1.0.0/bin/python -B backend/api/scripts/migrate_user_api_keys.py --generate-key`.
3. Store it as `USER_API_KEYS_ENCRYPTION_KEY` in the deployment secret store or an owner-only environment file. Do not reuse `JWT_SECRET_KEY`.
4. Deploy the code without restarting long-running ingestion jobs.
5. Run the read-only audit with the same locked runtime and Python safety flags: `PYTHONDONTWRITEBYTECODE=1 /root/data/python-runtimes/globemind-web/1.0.0/bin/python -B backend/api/scripts/migrate_user_api_keys.py`.
6. Run `--apply`, then run the audit again. It must report `plaintext=0`, and API profile responses must contain `api_keys: null` only.
7. Verify assistant requests using one test account, then remove the restricted backup according to the retention policy.

## Application encryption key rotation

1. Put the new key in `USER_API_KEYS_ENCRYPTION_KEY` and the previous key in `USER_API_KEYS_DECRYPTION_KEYS`.
2. Perform a controlled application restart and verify old API-key rows and every enabled or pending MFA enrollment can still be read.
3. Run `migrate_user_api_keys.py --apply` with the locked Web runtime to re-encrypt all database API-key rows with the new primary key.
4. Run the audit and a test assistant request. This migration does **not** rewrite append-only MFA enrollment events.
5. Keep the old key in `USER_API_KEYS_DECRYPTION_KEYS` while any active or pending MFA enrollment still references it. The current append-only identity-assurance ledger has no in-place re-encryption path; removing the fallback early makes those factors unavailable. Re-enroll affected factors or introduce and validate an append-only rewrap event under a separate reviewed migration before retiring the old key.
6. Only after both database rows and MFA ledger ciphertext have been proven independent of the old key may the fallback be removed, followed by a controlled restart and verification before revocation.

## JWT and identity-assurance integrity-key rotation

`JWT_SECRET_KEY` signs access tokens and derives the HMAC key for events under `IDENTITY_ASSURANCE_ROOT`. There is no dual-key verifier for that event chain. Do not rotate it as a routine application-only change.

1. Inventory active tracked sessions and verify the complete identity-assurance ledger with the current key without printing token or event contents.
2. Define an approved migration or retirement boundary for the existing ledger, including retention, rollback, user notification, and evidence preservation. Copying or rewriting events in place is prohibited.
3. Revoke or expire existing sessions through the normal control path and preserve the old ledger as restricted evidence.
4. Rotate the key only in a maintenance window, restart through the controlled runbook, and verify new login, MFA challenge, session revoke, and audit-chain behavior.
5. Record explicitly that pre-rotation sessions are invalid and that the pre-rotation local ledger is not verifiable with the new key unless an independently reviewed migration was completed.

## Database credential rotation

Deploy scripts that read the password from the process environment before rotating PostgreSQL. Stop or complete old loader processes whose command line contains `--password`, rotate the database credentials, update the restricted environment, and start the loaders through the controlled supervisor. Confirm `/proc/<pid>/cmdline` and service logs contain no password.

## Entity-governance HMAC-key rotation

`ENTITY_GOVERNANCE_HMAC_KEY` authenticates the append-only chain under `ENTITY_GOVERNANCE_ROOT`. It is deliberately separate from `JWT_SECRET_KEY`, but the current ledger stores neither a key ID nor a keyring and has no dual-key verifier. Replacing it in place makes all existing governance events fail closed.

1. Verify the complete governance chain with the current key and record only bounded counts and digests; do not print reasons, actor references, evidence metadata, or the key.
2. Freeze governance mutations through an approved maintenance procedure and preserve the old ledger as restricted evidence. Do not rewrite or remove events in place.
3. Define and review an append-only migration that retains the old chain head, event order and record digests, or explicitly retire the old ledger with retention, rollback and accountability evidence.
4. Install a new key of at least 32 bytes through the secret store, perform the controlled Web restart, and verify empty/new-chain status plus an authorized evidence-backed mutation in a disposable candidate environment.
5. Do not retire the old key until the retained pre-rotation ledger can still be independently verified or its approved retention period has ended. The checked-in code does not yet implement this migration.
